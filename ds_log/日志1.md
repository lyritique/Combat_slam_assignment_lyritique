## 第 1 轮：CMakeLists 第 7 行报错

**用户**：

```
CMake Error at CMakeLists.txt:7 (target_link_libraries):
  Cannot specify link libraries for target "src/main.cpp" which is not built
  by this project.

-- Configuring incomplete, errors occurred!
See also "/home/lyritique/project/improved_Task1/build/CMakeFiles/CMakeOutput.log"。
不要动文件，帮我看看有什么问题
```

**助手**：你的目录我一个字没动，全部测试都在 `/tmp/improved-check` 的副本里做的。

### 直接原因：`target_link_libraries` 的第一个参数必须是 target 名字

```cmake
add_library(func_shared SHARED include/func.cpp)
add_executable(improved_task src/main.cpp)
target_link_libraries (src/main.cpp include/func.cpp)   # ← 第 7 行
```

`target_link_libraries(<目标> <要链接的库...>)` 的第一个参数得是用 `add_library` 或 `add_executable` 创建过的目标名，不是文件名。CMake 收到 `src/main.cpp` 就去项目里找叫这个名字的目标，找不到，于是报 "which is not built by this project"。

你写的两个目标名分别是 `func_shared` 和 `improved_task`，所以这行应该是：

```cmake
target_link_libraries(improved_task PRIVATE func_shared)
```

另外第二个参数也不该是 `include/func.cpp`。链接器吃的是库（`func_shared` 这个目标，最终生成 `libfunc_shared.so`），源文件 `func.cpp` 已经被编进那个库里了，不需要也不能再当库链接一次。

### 改完这行还会撞上第二个错

我在副本里只改了第 7 行，配置通过了，但编译立刻报：

```
src/main.cpp:2:10: fatal error: func.h: No such file or directory
```

因为你在 `src/main.cpp` 里写的是 `#include <func.h>`——尖括号只搜索系统头文件路径和 `-I` 指定的目录，而你没有把 `include/` 加进搜索路径。两种改法，选一个：把尖括号改成引号 `#include "func.h"`，或者在 CMakeLists 里加一行

```cmake
target_include_directories(func_shared PUBLIC include)
```

用 `PUBLIC` 的好处是任何链接了 `func_shared` 的目标自动获得这个路径，以后加文件不用重复写。我在副本里用的是第二种，加上之后配置、编译、链接全部通过。

### 代码里有个逻辑反了

在 `main.cpp` 第 36-41 行：

```cpp
//判断point_z是否为正
if (point_z > 0)
    std::cout << "输入有问题，出现非正深度";

if (point_z > 0)
    return 0;
```

条件写反了。`point_z` 此时已经是相机坐标系的 `Zc`，大于 0 恰恰是合法深度，而你的代码把它当错误处理，打印报错并 `return 0`，正常情况一次都算不出来。反过来，真正非正的深度会一路走到第 44 行做除数。实测（用副本编译出的程序）：

| 输入 | Zc | 实际输出 |
|---|---|---|
| point_z = 3 | 8（合法） | 打印"输入有问题，出现非正深度"就退出，没有任何结果 |
| point_z = -10 | -5（非法） | 一路算完，输出 (-320, -1080)、距离 1142.31，也不报错 |

应该改成 `if (point_z <= 0)`，而且判断和 `return 0` 合成一个分支写清楚：

```cpp
if (point_z <= 0)
{
    std::cout << "输入有问题，出现非正深度\n";
    return 0;
}
```

顺便说，距离公式这次写对了：`std::hypot(u - 12, v - 13)` 用上了观测点 (12, 13)，量纲也对了。这是相对 Task1 那版的实质进步。

### 其他小问题

`cmake_minimum_required(VERSION 3.1)` 太老。你机器上是 3.22 能跑，但 CMake 4.0 起已经拒绝低于 3.5 的写法，别人 clone 下来可能直接失败。写 3.10 以上比较稳。

没有声明 C++17：

```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
```

`include/func.h` 里用了 `std::string` 却没 `#include <string>`。现在能过是因为 `main.cpp` 和 `func.cpp` 都先包含了 `<iostream>`，而 libstdc++ 的 iostream 间接带进了 string。头文件应该自己自足。

用 `SHARED` 建库有个后续影响：程序运行时需要能找到 `libfunc_shared.so`。在 `build/` 目录里直接跑没问题（CMake 自动写入了构建树 RPATH），但把可执行文件单独拷出去就会报找不到库。

还有一点结构性提醒：作业要求"分开头文件与实现文件"，你把 `getValue` 拆出去是对的，但重投影本身还全写在 main.cpp 里，外参也还是 `point_x * (-1) + 7` 这种展开写法。

## 第 2 轮：不改代码结构，但担心 shared 难以使用

**用户**：重投影计算包装成函数就算了，我暂时不会函数返回多值。展开写法也算了。问题是接下来的git版本管理，GitHub上clone不应该全copy下来了吗，不然shared不就极难用到吗

**助手**：你说得对，我上一轮那句话把结论说过头了。在 clone 场景下 SHARED 完全没问题，理由如下。

### 为什么 clone 之后一定好用

CMake 给构建树里的可执行文件写了一个 RUNPATH，指向构建目录：

```
0x000000000000001d (RUNPATH)  Library runpath: [/tmp/improved-check/build]
```

所以我做了个 A/B：把可执行文件单独拷到 `/tmp/dist/` 去跑。

- 库还在原来那个路径上时 → 正常运行，虽然可执行文件已经不在构建目录里了；
- 把 `libfunc_shared.so` 从那个路径挪走 → 立刻报

```
error while loading shared libraries: libfunc_shared.so: cannot open shared object file
```

（随后把库复原了，临时副本在 /tmp 里，你的目录没动。）

结论就是：可执行文件按 RUNPATH 里写死的绝对路径去找库，而 clone + 构建之后，那个路径上必然有 `libfunc_shared.so`，所以 `./build/improved_task` 照跑不误。构建树是一体的。我原本想提醒的场景是**把可执行文件从构建树里拎出去单独分发**——拷给同学、装到 `/usr/local/bin`、塞进 Docker 镜像的另一层，那种情况下才会真的报错。这个场景作业里碰不到，我不该拿它来质疑你的 CMakeLists。

### 那 git 到底该提交什么

提交：`CMakeLists.txt`、`src/`、`include/`、`README.md`、`.gitignore`

不提交：`build/` 整个目录，包括 `libfunc_shared.so` 和 `improved_task`

`.gitignore` 里一行就够：

```
build/
```

理由不是"库不能用"，而是构建产物是本机生成物：在 x86 上编的 `.so` 拷到别人的 ARM 机器上没意义，二进制文件出现在 diff 里也无法阅读评审。

作业的措辞是"**重新 clone 后能够构建运行**"，关键词是"构建"——不是"clone 完直接能跑"。所以正确姿势就是仓库里放源码加 CMakeLists，README 里写清

```bash
cmake -S . -B build && cmake --build build && ./build/improved_task
```

### 你决定跳过的两件事

重投影不包装成函数、外参保持展开写法，都行，作业没要求这两条。只有一处提醒：报告里"重投影原理"那一节，最好把 `R`、`t` 和三行标量运算的对应关系写一句，比如"`R = diag(-1,-1,1)` 展开后即 `Xc = -Xw + 7`"这类，否则读者看不出那三行就是在实现 `Pc = R * Pw + t`。

## 第 3 轮：GitHub 建仓库时的 .gitignore 选项

**用户**：我在github创建repository时也看见了add .gitigore,这个选项选它的模板还挺多样复杂，但我已经大致写完程序，一会启用git，推送到GitHub的remote仓库上，我想应该读不到remote仓库的gitignore，会在本地仓库产生大量无用log吗

**助手**：先纠正一个前提：GitHub 那个 `.gitignore` 选项**不是服务端配置**，它只是往新仓库里提交一个名叫 `.gitignore` 的普通文本文件。Git 客户端读的是**你工作区里的**那个文件，所以不存在"读不到"的问题——文件要么已经在你本地（clone/pull 之后），要么还没下来。

### 选了模板真正的后果：远端自带一个初始 commit

GitHub 勾选 README / .gitignore / license 中的任何一个，都会帮你生成一次初始提交。你在本地 `git init` 之后是另一条独立的历史线，两边没有共同祖先。这时 push 会被拒：

```
! [rejected]  main -> main (fetch first)
```

解决办法是 pull 下来合并或变基，这才是唯一会产生"多余 log"的地方：一个 merge commit；如果两边都建了 `.gitignore`，还会撞一次冲突。

所以最省事的是**让 GitHub 建一个完全空的仓库**，不勾任何东西。如果已经建好了，两个选择：趁刚建、还没人用，删掉重建；或者

```bash
git pull --rebase origin main
```

如果 git 拒绝（提示 unrelated histories），换成 `git pull --no-rebase --allow-unrelated-histories origin main`，代价是多一个 merge commit。

### 会产生大量无用 log 吗

`.gitignore` 本身不会，一个文件、最多一次 commit。真正会制造大量垃圾历史的是**顺序搞反**：先 `git add .` 把 `build/` 收进去并提交，之后才想起来要忽略。那时：

- `build/` 里那几十个文件都会记进历史，对象永久留在 `.git` 里
- 事后 `git rm -r --cached build` 加进 `.gitignore` 只是"停止跟踪"，历史里那些文件照样在
- 想彻底清掉得重写历史，麻烦且有风险

关键就是一条：**先写 `.gitignore`，再 `git add`**。

### 建议的操作顺序

```bash
cd /home/lyritique/project/improved_Task1
printf 'build/\n' > .gitignore
git init -b main            # 不加 -b 会建出 master，和 GitHub 的 main 对不上
git status                  # 关键检查：这里不该出现 build/ 里的任何文件
git add .
git status
git commit -m "feat: 实现重投影计算"
git remote add origin <仓库地址>
git push -u origin main
```

### 两个会当场卡住的点

第一，认证。当时机器上没有 SSH 密钥，也没有配置 credential helper。GitHub 早就禁用了账号密码推送：走 HTTPS 必须用 Personal Access Token 当密码，走 SSH 得先生成密钥并贴到 GitHub。

```bash
ssh-keygen -t ed25519 -C "3650808550@qq.com"
cat ~/.ssh/id_ed25519.pub
```

第二，提交身份。`~/.gitconfig` 里是 `lyritique / 3650808550@qq.com`，能正常提交。但 Git 是靠邮箱把 commit 关联到 GitHub 账号的，这个邮箱如果没加进 GitHub 账号，提交记录不会显示成你的头像和用户名。

### 按作业要求安排

作业要求"分支开发、提交、推送和一次 PR 合并"，所以别把代码一把推到 main 上：

```bash
git switch -c feature/reprojection
# 写代码、提交
git push -u origin feature/reprojection
```

到 GitHub 上开 PR 合并进 main，报告里填 PR 链接和合并后的 commit hash。

## 第 4 轮：SSH 是否必需，以及 .gitignore 评审

**用户**：我github邮箱的确是这个。我必需要搞ssh吗。你看看我的.gitignore可以吗

**助手**（第一次检查时发现 `.gitignore` 是 0 字节的空文件）：

### SSH 不是必须的

三条路任选一条：

**在 VS Code 面板里推**（最省事）。如果你在 VS Code 里登录过 GitHub 账号，源代码管理面板点"发布分支"或"推送"时会用 VS Code 自己的 OAuth 令牌，不需要 SSH、也不需要造 token。

**HTTPS + Personal Access Token**。remote 用 `https://github.com/<用户名>/<仓库名>.git`，push 时让你输密码的地方粘贴 PAT（GitHub → Settings → Developer settings → Personal access tokens，classic token 勾 `repo` 权限）。想让它记住：

```bash
git config --global credential.helper store
```

代价是 token 明文存在 `~/.git-credentials`，以及 token 有有效期。

**SSH**。一次配置长期免密，代价是要生成密钥、把公钥贴到 GitHub。

你这台机器是远程开发环境，综合看：VS Code 面板推最省事；如果坚持命令行，SSH 比 PAT 值得配一次，因为它不会有"半年后突然推不上去"的问题。

### 你的 .gitignore

第一次检查时它是空文件，等于没写。用户在编辑器里补上内容后重新检查，实测结果：

```
.gitignore:1:build*/     build/CMakeCache.txt
.gitignore:1:build*/     build/libfunc_shared.so
.gitignore:2:*.o         include/func.o
.gitignore:3:*.a         libfunc.a
```

`build/` 里那 37 个文件全被挡住了，`git add -A` 之后只有 7 个文件进入暂存区。`*.o`、`*.a`、`*.so` 这三条也按预期生效。

两点补充：

**`a.out` 现在会被提交。** 实测放在根目录的 `a.out` 没有被任何规则命中。加一行 `a.out` 就行。

**`.vscode/` 现在会被提交**，这是需要你判断的一条。提交它能让别人复现你的调试配置，但里面的设置常带本机绝对路径（例如 Task1 里的 `"cmake.sourceDirectory": "/home/lyritique/project/Task1"`），推到公开仓库会显得脏。作业没要求提交它，建议先忽略。

建议的最终内容：

```

*.a
*.so
a.out
.vscode/
```

另外 `build*/` 比 `build/` 略宽，也会匹配 `build-debug/` 这类目录，对当前项目没坏处；唯一隐患是将来如果你建一个叫 `builder/` 之类的源码目录会被误伤。还有一条通用规则：`.gitignore` 对**已经被跟踪的文件**无效，所以顺序永远是先写好规则再 `git add`。

## 第 7 轮：分支开发到底怎么走

**用户**：不是说要分支开发吗，我先提交一个，在推送到GitHub，再添加一个，再推送到GitHub

**助手**：你的直觉有一半是对的：**第一次必须先推到 GitHub，因为远端得先有 main 分支，否则 PR 没有目标分支可指向**。但后半段要改——第二次不能继续往 main 上提交，那样就永远没有 PR 了。

### 先分清两件事

`commit` 是本地记录一次历史，`push` 是把本地分支同步到远端。不是绑定的：你可以在分支上连续提交好几次，最后一次性 push。"分支开发"的意思是 main 只用来接收合并，真正的开发在另一条分支上进行，做完通过 PR 合回 main：

```
main    :  A(初始化) ──────────────● 合并（PR）
                 \                /
func    :         B ── C ────────
```

### 针对当前状态的具体做法

第一步，先把 main 收拾干净并推上去：

```bash
cd /home/lyritique/project/improved_Task1
git reset
git add .gitignore
git commit -m "chore: 初始化仓库与忽略规则"
git remote add origin <你的仓库地址>
git push -u origin main
```

第二步，开分支做开发。想分两次提交，就把两次都放在分支上：

```bash
git switch -c feature/reprojection

git add src/main.cpp
git commit -m "feat: 实现重投影计算与像素误差度量"

git add CMakeLists.txt include
git commit -m "feat: 拆分输入函数到头文件与实现文件，接入 CMake 构建"

git push -u origin feature/reprojection
```

`git switch -c` 只是移动一个指针，不会复制文件，工作区里的东西原封不动就带过来了。三次提交对应两次 `commit`，但只 push 一次。

第三步，在 GitHub 上开 PR，标题写"实现重投影计算"，描述里写清做了什么、怎么验证的，合并方式选默认的 "Create a merge commit"。

第四步，本地同步：

```bash
git switch main
git pull
```

### 一个顺序上的提醒

别把 CMakeLists.txt 放进 main 的初始提交。因为那个文件里写着 `add_executable(improved_task src/main.cpp)`，而源码是在分支上才进去的。把构建文件和源码一起放进 feature 分支，main 的初始提交只留 `.gitignore`，这样每个状态的 main 都是自洽的。

```
fatal: unable to access 'https://github.com/lyritique/Combat_slam_assignment_lyritique.git/': Failed to connect to github.com port 443 after 3 ms: Connection refused
```

**助手**：这是网络层的问题，不是 git 的问题。经用户同意做了两次免沙箱的只读探测。

### 结论：Windows 的 hosts 文件把 github.com 指到了本机

`getent hosts github.com` 返回的是 **`127.0.0.1`**。访问 github.com 时系统被导到自己这台机器上，而本机 443 端口没有任何程序在听，内核立刻回一个 RST——这就是"3 毫秒就 Connection refused"的来源。正常连 GitHub 的几个官方 IP 是通的：

```
20.205.243.166    HTTP 200  connect=0.149s
140.82.113.4      HTTP 200  connect=0.305s
```

罪魁在 Windows 那边的 hosts 文件（`C:\Windows\System32\drivers\etc\hosts`）里，里面有几百行 `127.0.0.1`：

```
127.0.0.1 github.com
127.0.0.1 api.github.com
127.0.0.1 raw.githubusercontent.com
127.0.0.1 github.githubassets.com
127.0.0.1 gist.github.com
127.0.0.1 objects.githubusercontent.com
...
```

WSL 里的 `/etc/hosts` 是干净的，但 WSL 的 DNS 查询会转发给 Windows 的解析器（`nameserver 10.255.255.254` 就是宿主机），而 Windows 解析时会先读它自己的 hosts，于是这个 `127.0.0.1` 就漏进 WSL 了。

绕开 DNS、直接连真实 IP 是通的：

```
curl --resolve github.com:443:140.82.113.4 https://github.com
→ HTTP 200  连接耗时 0.288s
```

百度也通（HTTP 200）。所以网络本身没问题，GitHub 也没被墙，纯粹是域名被本地劫持了。

这也意味着**改用 SSH 一样不行**——SSH 和 HTTPS 都要先解析 github.com，解析出来还是 127.0.0.1。所以不用去配密钥或 token，问题不在认证那一层。

### 三种修法

**方案 A：改 Windows 的 hosts（治本）**

用管理员身份打开记事本：

```powershell
notepad C:\Windows\System32\drivers\etc\hosts
```

先另存一份 `hosts.bak` 做备份，然后删掉所有带 `github` 的行，保存。然后：

```powershell
ipconfig /flushdns
wsl --shutdown
```

**方案 B：在 WSL 里临时绕过（重启失效）**

```bash
sudo sh -c 'echo "140.82.113.4 github.com" >> /etc/hosts'
nslookup github.com 223.5.5.5    # 想查更新的 IP 可以用这条
```

`/etc/hosts` 是 WSL 自动生成的，每次重启都会被覆盖，所以这只是应急。

**方案 C：让 WSL 不再走 Windows 的解析（持久）**

```bash
sudo tee /etc/wsl.conf > /dev/null <<'EOF'
[network]
generateResolvConf = false
EOF

sudo rm /etc/resolv.conf
sudo sh -c 'echo "nameserver 223.5.5.5" > /etc/resolv.conf'
```

然后 `wsl --shutdown` 重进。

### 真正的错误在 CMakeLists.txt 第 9 行

```cmake
target_link_libraries (func_shared PUBLIC include)
```

这行把两个不同的命令混成一个了。`target_link_libraries` 的第一参数是"要操作的目标"，第二参数开始是**要链接的库**。写成 `func_shared` 加 `include`，CMake 就理解成"给 func_shared 这个库链接一个叫 include 的库"，于是链接器去找 `libinclude.so`，找不到。复现的报错是：

```
/usr/bin/ld: cannot find -linclude: No such file or directory
collect2: error: ld returned 1 exit status
```

注意 configure 阶段是**通过**的，错误只在 build 阶段出现——所以只跑配置看不出问题。

### 这里其实是两件事，得分成两行

```cmake
add_library(func_shared SHARED include/func.cpp)         # 建库，目标是 func_shared
add_executable(improved_task src/main.cpp)               # 建可执行文件

target_include_directories(func_shared PUBLIC include)   # 头文件搜索路径：编译时加 -Iinclude
target_link_libraries(improved_task PRIVATE func_shared) # 库链接：链接时加 -lfunc_shared
```

`target_include_directories` 管的是"去哪儿找 `func.h`"，对应编译阶段的 `-I` 参数；`target_link_libraries` 管的是"连哪个库"，对应链接阶段的 `-l` 参数。一个给编译器看，一个给链接器看，不能合并成一行。`PUBLIC` 写在 include 这条上，意思是链接了 func_shared 的目标自动继承这个头文件路径。

在副本里按上面改完，配置、编译、运行全通过：

